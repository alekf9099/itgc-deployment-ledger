# 배포 관리 대장 사용 안내

ITGC PC-01 / PD-02 대응 배포 관리 대장의 화면별 사용 방법입니다.

- **대상 통제** PC-01 애플리케이션 변경 승인 및 개발자/사용자 테스트, PD-02 데이터 정합성 테스트
- **통제부서** QA유닛 · **검토부서** TA유닛
- **근거** 「릴리즈 유형별 QA/QC 증적 수립 표준 가이드라인」
- **적용 버전** v2.5.0

이 문서는 대장과 함께 버전 관리됩니다. 화면이 바뀌면 이 문서도 같은 PR에서 갱신합니다.

## 화면 구성

로그인하면 좌측에 메뉴가 표시됩니다.

```
배포 관리 대장
ITGC PC-01 / PD-02 · QA유닛
────────────────────────
01 대장
02 월간 점검
03 작성 기준
04 변경 이력
05 계정 관리        ← 관리자에게만 표시
06 저장소
────────────────────────
성명 · 소속
아이디 · 권한
비밀번호 변경 · 로그아웃
────────────────────────
통제부서 QA유닛
검토부서 TA유닛
v2.5.0              ← 현재 버전
```

좌하단 버전 표기는 어느 버전의 대장에서 작성·판정된 기록인지 확인하기 위한 값입니다.
화면 동작이 이 문서와 다르면 먼저 버전을 확인하십시오.

### 불러오는 중 표시

표나 통계를 불러오는 동안 **회색 막대(스켈레톤)** 가 표시됩니다.
들어올 내용의 형태를 미리 보여주는 것이며, 잠시 후 실제 값으로 바뀝니다.

회색 막대가 계속 사라지지 않으면 서버 응답이 지연되는 상태입니다.
새로고침 후에도 같으면 QA유닛에 알리십시오.

## 1. 로그인

### 접속

담당자별로 발급받은 아이디와 비밀번호로 로그인합니다. **계정을 공유하지 마십시오.**
모든 등록·수정·삭제가 로그인한 계정의 이름으로 기록되므로, 계정을 공유하면
누가 수행했는지 특정할 수 없어 책임 추적성이 성립하지 않습니다.

로그인 성공 자체도 변경 이력에 기록됩니다.

### 최초 로그인

계정을 발급받으면 관리자로부터 **임시 비밀번호**를 전달받습니다.
이 값은 발급 시 한 번만 표시되므로 관리자도 다시 확인할 수 없습니다.

최초 로그인 후 좌측 하단 **`비밀번호 변경`** 에서 즉시 변경하십시오.

| 항목 | 내용 |
|---|---|
| 현재 비밀번호 | 전달받은 임시 비밀번호 |
| 새 비밀번호 | **10자 이상** |
| 새 비밀번호 확인 | 위와 동일하게 입력 |

현재 비밀번호가 틀리면 변경되지 않습니다. 변경 사실은 변경 이력에 기록되며,
비밀번호 값 자체는 어디에도 기록되지 않습니다.

### 오류 메시지

| 메시지 | 원인과 조치 |
|---|---|
| 아이디 또는 비밀번호가 올바르지 않습니다. | 아이디 존재 여부를 노출하지 않기 위해 두 경우를 같은 메시지로 처리합니다. 재확인 후 재시도하고, 계속 실패하면 관리자에게 비밀번호 재설정을 요청하십시오. |
| 비활성화된 계정입니다. 관리자에게 문의하십시오. | 인사 이동·퇴사 등으로 회수된 계정입니다. |
| 세션이 만료되었습니다. 다시 로그인하십시오. | 로그인 후 12시간이 지났습니다. 다시 로그인하십시오. |
| 서버에 연결하지 못했습니다. | 일시적인 네트워크 또는 서버 오류입니다. 잠시 후 재시도하고 반복되면 QA유닛에 알리십시오. |

### 세션

로그인 상태는 **12시간** 유지되며, 이후 자동으로 만료됩니다.
공용 PC에서는 작업을 마친 뒤 반드시 **`로그아웃`** 하십시오.

## 2. 대장

**이 화면의 목록 전체가 PC-01 모집단입니다.** 배포 이력 전수를 기재하고,
각 건을 증적 문서와 1:1로 연결합니다.

### 입력 시작점

대장 입력은 **보고서 등록 시점이 아니라 배포 이력을 기준으로 시작합니다.**
GitHub RELEASE 머지 PR 목록에서 건을 먼저 만들고, 대응하는 보고서를 찾아
증적 문서 ID를 채웁니다. **보고서가 없는 건이 곧 미비 건입니다.**

보고서가 등록된 건만 기재하면 미비 건이 대장에서 사라져 모집단이 왜곡됩니다.

### 상단 통계

| 카드 | 의미 |
|---|---|
| 모집단 (필터 적용) | 현재 필터 조건에 해당하는 건수 |
| 확인필요 | 판정 항목 중 하나 이상이 이상값인 건수. 조치 대상입니다 |
| 정규 / 수시 / 핫픽스 | 유형별 분포 |
| 보완필요 (전체 누적) | 증적 상태가 「보완필요」인 건수. 필터와 무관하게 전체 범위로 집계하여 이월 관리합니다 |

### 검색과 필터

| 항목 | 대상 |
|---|---|
| 검색 | 증적 문서 ID · 대상 시스템 · 일감 · 담당자(작성자·검증자·승인자·판정자) |
| 유형 전체 | 정규 / 수시 / 핫픽스 |
| 판정 전체 | 확인필요 / 정상 |
| 배포일 시작 · 종료 | 배포일 기준 범위 |
| 초기화 | 모든 필터 해제 |

### 판정 스트립

각 행 맨 앞의 여섯 칸이 판정 결과입니다. 칸에 마우스를 올리면 항목명과 판정값이 표시됩니다.

| 순서 | 항목 | 정상 조건 |
|---|---|---|
| 1 | 기한 준수 | 증적 등록일이 등록 기한 이내 |
| 2 | 직무 분리 | 변경 작성자와 검증 수행자가 다름 |
| 3 | 승인 기록 | 배포 승인자와 승인일이 모두 기재됨 |
| 4 | 증적 매핑 | 증적 문서 ID가 기재됨 |
| 5 | 정합성 확인 | 스키마 변경 「해당」 시 검증 「완료」 + 검증자 기재 |
| 6 | ID 정합성 | ID의 유형코드가 릴리즈 구분과, 날짜부가 배포일과 일치 |

색은 다음과 같습니다.

- **초록** 정상
- **붉음** 이상 — 조치 필요
- **회색** 해당 없음 또는 미판정 — 이상이 아닙니다

회색 칸은 두 경우가 있어 색만으로는 구분되지 않습니다. 마우스를 올려 확인하십시오.

- **해당없음** 그 항목이 이 건에 적용되지 않음 (예: 스키마 변경이 「없음」인 건의 정합성 확인)
- **미판정** 판정에 필요한 값이 아직 입력되지 않음

**여섯 항목 중 하나라도 붉으면 그 행 전체가 붉게 표시되고 「확인필요」로 분류됩니다.**

> **판정값은 직접 수정할 수 없습니다.** 입력값에서 계산되며 저장되지 않습니다.
> 판정을 임의로 정할 수 있으면 통제의 신뢰성이 사라지기 때문입니다.

### 배포 건 등록

우측 상단 **`배포 건 추가`** 를 누르면 입력 화면이 열립니다.
상단의 「자동 판정」 영역이 입력에 따라 실시간으로 갱신되므로,
저장 전에 어떤 항목이 미비인지 확인할 수 있습니다.

#### 모집단 식별

| 항목 | 설명 |
|---|---|
| 배포일 | 실제 운영 반영일. 배포 이력(GitHub RELEASE 머지 PR)과 일치해야 합니다 |
| 릴리즈 구분 | 정규 / 수시 / 핫픽스. 배포 요청 시점에 판정합니다 |
| 증적 문서 ID | **배포일과 릴리즈 구분을 먼저 고르면 자동 생성됩니다** |
| 대상 시스템 | 배포가 반영된 서비스·시스템명. 리포지토리 단위 배포는 리포지토리명을 함께 적습니다 |
| 유형 판정자 | 릴리즈 유형을 판정한 담당자. 차등 증적 적용의 근거이므로 공란으로 두지 않습니다 |
| 일감 / 릴리즈 식별자 | 정규는 릴리즈 회차·프로젝트명, 수시는 COW 번호, 핫픽스는 조치 내용 요약 |

증적 문서 ID 형식은 **`QA-{유형코드}-{배포일 YYYYMMDD}-{일련 2자리}`** 입니다.

| 유형 | 코드 | 예 |
|---|---|---|
| 정규 | R | `QA-R-20260814-01` |
| 수시 | A | `QA-A-20260814-01` |
| 핫픽스 | E | `QA-E-20260814-01` |

같은 배포일·같은 유형 안에서 01부터 부여되며, 이미 있는 번호는 자동으로 다음 값이 됩니다.

> **다음 중 하나라도 해당하면 일감 건수와 무관하게 정규로 취급합니다** — DB 스키마 변경 또는
> 데이터 마이그레이션, 인증·권한·과금 로직 변경, 외부 연동 규격 변경, 신규 화면 또는
> 신규 기능 추가, 다수 일감 묶음 배포 또는 서비스 개편.

#### 검증 및 승인

| 항목 | 설명 |
|---|---|
| 변경 작성자 | 변경을 작성한 담당자 |
| 검증 수행자 | **변경 작성자와 같을 수 없습니다.** 같으면 직무 분리 위반으로 판정됩니다 |
| QA 판정 | 통과 / 조건부 통과 / 실패(반려) |
| 배포 승인자 | PC-01 승인 요건. GitHub PR 머지 기록(Merged by)이 있으면 그 값을 기준으로 기재합니다 |
| 배포 승인일 | 승인자와 함께 있어야 승인 기록이 완비로 판정됩니다 |
| 증적 등록일 | 보고서를 아카이빙 채널에 등록한 날짜. **기한 준수 판정의 기준값입니다** |
| 증적 등록 경로 | 게시판 경로 또는 URL |

판정은 **문자열 비교**입니다. 같은 사람을 다르게 표기하면 직무 분리가
잘못 판정되므로 표기를 통일하십시오.

#### 데이터 정합성 (PD-02)

| 스키마·데이터 변경 | 정합성 검증 | 정합성 검증자 | 판정 |
|---|---|---|---|
| 해당 | 완료 | 기재 | 정상 |
| 해당 | 부적합 · 미실시 | — | 비정상 |
| 해당 | 완료 | 공란 | 비정상 |
| 없음 | 공란 | 공란 | 미해당 (이상 아님) |
| 없음 | 값 있음 | — | 비정상 — 기재 오류이며 월간 점검에서 입력 오류로 분리 집계됩니다 |

스키마 변경이 「없음」인 건은 정합성 칸을 **비워두십시오.**

#### 상태 및 예외

| 증적 상태 | 의미 |
|---|---|
| 작성중 | 보고서 작성 진행 중 |
| 등록완료 | **작성자가 아닌 QA유닛이 확인 후 지정합니다** |
| 보완필요 | 반송 상태. 해소될 때까지 이월 관리됩니다 |
| 예외승인 | 기한 초과·항목 축약을 승인받은 건 |
| 해당없음 | 소스코드 변경이 없어 증적 대상이 아닌 건. **사유를 비고에 적습니다** |

**예외 승인자** 는 등록 기한을 초과하거나 증적 항목을 축약한 경우에만 기재합니다.
승인 권한자는 QA유닛 책임자입니다. 초과·축약이 발생했는데 공란인 건은 미비 건으로 관리됩니다.

#### 등록 기한

| 릴리즈 구분 | 기한 |
|---|---|
| 정규 | 배포일 (배포 승인 요청 전 작성) |
| 수시 | 배포일 + 3영업일 |
| 핫픽스 | 배포일 + 2영업일 |

영업일은 주말을 제외하고 계산합니다. 계산된 기한은 표의 「기한」 열과
입력 화면의 「등록 기한」에 표시됩니다.

#### 저장

저장하려면 **배포일 · 릴리즈 구분 · 대상 시스템 · 유형 판정자** 네 항목이 필요합니다.
나머지 항목은 비어 있어도 저장되지만, 해당 판정이 「미완비」·「매핑미완료」로 남아
확인필요로 분류됩니다. 작성 중인 건을 일단 등록해두고 값을 채워 나가는 방식을 전제한 것입니다.

| 버튼 · 단축키 | 동작 |
|---|---|
| `저장` · `Ctrl+Enter` | 저장하고 입력 화면을 닫습니다 |
| `저장 후 계속` · `Ctrl+Shift+Enter` | 저장하고 다음 건 입력을 이어서 시작합니다 |

#### 연속 입력 보조

같은 날 여러 건을 등록하는 경우를 위해 입력 부담을 줄이는 장치가 있습니다.

| 기능 | 내용 |
|---|---|
| 직전 값 이어받기 | 새 건을 열면 **배포일**과 **대상 시스템**이 직전에 저장한 값으로 채워지고, 상단에 이어받은 항목이 표시됩니다. 다르면 수정하십시오 |
| 대상 시스템 자동완성 | 입력란을 누르면 기존에 사용한 시스템명이 목록으로 나타납니다. 목록에 없는 값도 그대로 입력할 수 있습니다 |
| 증적 등록일 `오늘` | 오늘 날짜를 한 번에 입력합니다 |
| 증적 문서 ID 자동 부여 | 배포일과 릴리즈 구분을 고르면 자동 생성되며, 같은 날·같은 유형의 다음 일련번호가 부여됩니다 |

> **릴리즈 구분과 담당자 이름은 이어받지 않습니다.**
> 유형 판정과 검증 주체는 건별로 확인해야 하는 값입니다. 미리 채워두면
> 확인 없이 저장하게 되어 판정의 근거가 약해집니다.
> 담당자 이름도 자동완성하지 않습니다 — 다만 판정이 문자열 비교이므로
> **표기를 통일**해 입력하십시오.

증적 문서 ID 는 **중복될 수 없습니다.** 이미 쓰인 ID 를 넣으면 저장되지 않습니다.
증적과 배포 건을 1:1 로 잇는 값이기 때문입니다.

### 배포 건 수정

표 우측의 **`편집`** 을 누릅니다. 입력 화면 하단 **「변경 이력」** 에서
이 건의 최초 등록자·최종 수정자와, 어떤 항목이 어떤 값에서 어떤 값으로
바뀌었는지 확인할 수 있습니다.

> **이미 부여된 증적 문서 ID 는 자동으로 바뀌지 않습니다.**
> 편집 중에 배포일이나 릴리즈 구분을 고쳐도 ID 는 그대로 유지됩니다.
> 값이 어긋나면 「ID 정합성」이 **불일치**로 표시되므로, 부여 오류인지
> 유형 재판정 이력인지 확인해 사유를 비고에 남기십시오.
>
> ID 를 실제로 바꿔야 한다면 직접 수정하십시오. 다만 아카이빙 채널의
> 보고서 제목도 함께 고쳐야 매핑이 유지됩니다.

### 배포 건 삭제

**관리자만 가능하며, 기록은 삭제되지 않습니다.** 대장에서 제외 표시만 하고
행 자체는 남습니다. 흔적 없는 삭제가 가능하면 모집단 완전성을 담보할 수 없기 때문입니다.

되돌리려면 관리자가 DB에서 직접 처리해야 하므로, 잘못 등록한 건은
삭제보다 수정으로 처리하십시오.

### CSV 내보내기

현재 필터가 적용된 목록을 CSV로 내보냅니다. 판정 결과와 등록 기한이 함께 포함됩니다.

**내보내기는 증적 반출로 기록됩니다** — 수행자·일시·건수와 함께 **적용된 필터가
범위로 기록**됩니다. 범위가 남지 않으면 그 반출본이 전수인지 일부인지 확인할 수 없습니다.

## 3. 월간 점검

QA유닛이 **월 1회** 수행합니다. **지적사항이 없어도 이력을 남깁니다.**
이력의 연속성 자체가 통제 운영의 증거입니다.

집계 기간은 **배포일 기준**이며, 점검 수행일은 기간 말 배포 건의 등록 기한이 지난
**익월 초**로 정합니다. 기한이 지나지 않은 건을 미비로 집계하지 않기 위해서입니다.

화면을 열면 대상 기간이 **전월 1일 ~ 전월 말일**, 점검 수행일이 오늘로 자동 설정됩니다.

### 01 점검 개요

점검 대상 통제·근거·주체·방법이 고정 표기되어 있습니다.
아래 입력 항목을 채웁니다.

| 항목 | 내용 |
|---|---|
| 대상 기간 시작 · 종료 | 배포일 기준 |
| 점검 수행일 | 실제 점검을 수행한 날 |
| 점검자 | 로그인한 계정의 성명이 기본 입력됩니다 |
| 확인자 | QA유닛 책임자 |

### 02 모집단 완전성 확인

**PC-01에서 가장 먼저 검증되는 항목입니다.**

GitHub RELEASE 머지 PR 목록의 건수를 세어 **「배포 이력 건수」** 에 입력합니다.
**「대장 기재 건수」** 는 기간 내 대장 건수가 자동 표시됩니다.

| 결과 | 의미 |
|---|---|
| 일치 | 모집단 완전성 확인 |
| 불일치 (차이 N건) | 원인을 규명하고 누락 건을 대장에 추가한 뒤, **「차이 원인 및 조치」** 에 기재 |

### 03 점검 항목별 결과

기간 내 배포 건에서 자동 집계됩니다. **지적 항목**과 **확인 항목**으로 나뉩니다.

#### 지적 항목 — 1건 이상이면 조치 내용 기재가 필수입니다

| 항목 | 통제 | 판단 기준 |
|---|---|---|
| 증적 매핑 누락 | PC-01 | 증적 문서 ID 미기재. 0건이어야 합니다 |
| 배포 승인 기록 누락 | PC-01 | 승인자 또는 승인일 미기재. 0건이어야 합니다 |
| 직무 분리 위반 | PC-01 | 변경 작성자와 검증 수행자가 동일. 0건이어야 합니다 |
| 정합성 검증 미이행·부적합 | PD-02 | 스키마 변경 건 중 검증 미실시 또는 부적합. 0건이어야 합니다 |
| 증적 등록 기한 초과 | PC-01 | 예외 승인이 없는 초과 건은 미비 건으로 관리 |
| 유형 판정자 미기재 | PC-01 | 차등 증적 적용의 근거 부재. 0건이어야 합니다 |
| 증적 문서 ID 정합성 불일치 | PC-01 | 유형코드 또는 날짜부 불일치. 사유를 확인합니다 |
| 입력 오류 (항목 간 모순) | PD-02 | 스키마 변경 「없음」인데 정합성 검증값이 있는 건. 즉시 정정 |
| 보완필요 미해소 (전체 누적) | PC-01 | 반송 후 미해소 건. **과거 기간을 포함한 전체 범위**로 집계 |

#### 확인 항목 — 지적사항이 아니며 후속 조치 이행 여부만 확인합니다

| 항목 | 확인 내용 |
|---|---|
| 예외 승인 건 | 예외 승인자 기재 여부와 승인 사유의 타당성 |
| 실패(반려) 건 | 재검증 및 보고서 재작성 완료 여부 |
| 조건부 통과 건 | 잔여 이슈에 대한 후속 조치 완료 여부 |

조치 내용은 입력을 멈추면 **자동으로 초안 저장**되므로, 작성 중 화면을 벗어나도 값이 남습니다.

### 04 표본 재검토

QA유닛이 직접 검증하지 않은 건 중 일부를 표본으로 확인합니다.
형식 점검만으로는 담보되지 않는 검증 품질을 보는 절차입니다.

증적 문서 ID, 선정 사유, 재검토 결과, 미비 사항 및 조치를 기재합니다.

### 05 점검 결과

지적 항목 수에 따라 자동으로 결정됩니다.

| 지적 항목 | 결과 |
|---|---|
| 0건 | **적정 · 지적사항 없음** |
| 1건 이상 | **보완 필요** |

점검자 의견을 기재합니다.

### 06 점검 이력 · 저장

**`점검 결과 저장`** 을 누르면 이력에 누적됩니다. 저장 조건은 다음과 같습니다.

- 대상 기간(시작·종료), 점검 수행일, 점검자가 입력되어 있어야 합니다
- 지적 항목이 1건 이상이면 **해당 항목의 조치 내용이 모두 기재**되어 있어야 합니다

저장된 이력은 행별로 **`CSV`** 로 내보낼 수 있습니다.
**`삭제`** 는 관리자만 가능하며, **기록은 실제로 지워지지 않습니다.** 이력에서 제외 표시만 하고
내용은 남습니다. 점검 이력의 연속성이 통제 운영의 증거이므로, 흔적 없이 사라지면 확인할 수 없습니다.

집계는 **서버가 대장에서 다시 계산한 값**이 저장됩니다. 화면에 보이는 수치와 저장되는 수치가
같으며, 화면에서 임의로 바꿀 수 없습니다.

점검 결과 CSV 내보내기도 증적 반출로 기록됩니다.

## 4. 작성 기준

「릴리즈 유형별 QA/QC 증적 수립 표준 가이드라인」을 화면에 옮긴 참조 문서입니다.
입력 중 판단이 필요할 때 확인합니다. **가이드라인이 개정되면 이 화면도 함께 갱신합니다.**

| 절 | 내용 |
|---|---|
| 01 입력 항목 | 각 입력 항목의 정의와 기재 규칙 (증적 문서 ID 체계, 릴리즈 구분 판정 기준, 담당자 표기, 증적 상태, 예외 승인 등) |
| 02 자동 판정 | 등록 기한 계산식과 여섯 판정 항목의 판단 규칙 |
| 03 유형별 보고서 작성 범위 | QA 완료 보고서 항목이 유형별로 필수 / 해당 시 / 미적용 중 무엇인지 |
| 04 운영 규칙 | 모집단·관리 주체·입력 시작점·증적 무결성·계정 및 권한·변경 이력·기록 보존·증적 반출 등 운영 원칙 |

각 항목은 접힌 상태로 표시되며 제목을 누르면 펼쳐집니다.

**「03 유형별 보고서 작성 범위」의 「미적용」 항목은 해당 유형에서 작성 대상이 아니므로
공란이어도 미작성으로 보지 않습니다.** 차등 적용의 근거가 되는 규정입니다.

## 5. 변경 이력

**모든 로그인 계정이 열람할 수 있습니다.** 열람 전용 계정도 볼 수 있으므로,
통제검토부서와 감사인이 직접 확인할 수 있습니다.

대장에 대한 모든 변경과 접속을 기록합니다. 누가·언제·어떤 항목을 어떤 값으로
바꿨는지가 PC-01 변경 통제의 증거입니다.

> **이 기록은 화면에서 수정하거나 삭제할 수 없습니다.** 수정·삭제 경로가 아예 없습니다.

|---|---|
| 등록 | 배포 건 신규 등록 |

| 대장 반출 · 점검 결과 반출 · 전체 백업 반출 | CSV 내보내기 (범위·건수 포함) |

### 조회

| 항목 | 대상 |

하단 「변경 이력」을 확인하는 편이 빠릅니다.

## 6. 계정 관리

**관리자(admin) 계정에만 표시됩니다.** 다른 권한으로 로그인하면 메뉴가 나타나지 않고,
주소를 직접 호출해도 서버가 차단합니다.

계정 발급·권한 변경·비활성화·비밀번호 재설정을 이 화면에서 수행합니다.
**모든 조작이 변경 이력에 기록됩니다.**

### 권한 선택

| 권한 | 부여 대상 | 가능한 일 |
|---|---|---|
| 관리자 | QA유닛 책임자 | 계정 관리, 배포 건 대장 제외, 점검 이력 삭제, 아래 모든 권한 |
| 작성 권한 | 대장을 작성하는 QA유닛 담당자 | 배포 건 등록·수정, 월간 점검 수행 |
| 열람 전용 | 통제검토부서(TA유닛), 감사인 | 조회 및 CSV 내보내기만 |

### 계정 발급

**`계정 추가`** → 아이디 · 성명 · 소속 유닛 · 권한 입력 → **`발급`**

- **아이디는 이후 변경할 수 없습니다.** 사내 계정 체계와 일치시키십시오
- **성명은 대장에 기록되는 이름입니다.** 판정이 문자열 비교이므로 표기를 통일하십시오
- 발급 직후 **임시 비밀번호가 한 번만 표시됩니다.** `복사` 버튼으로 복사해 본인에게 전달하고,
  최초 로그인 후 변경하도록 안내하십시오
- 임시 비밀번호는 **다시 확인할 수 없습니다.** DB에는 해시만 저장됩니다

### 권한 변경

해당 행의 권한 드롭다운을 변경합니다. 확인 후 즉시 적용되며 변경 이력에 기록됩니다.

### 비밀번호 재설정

담당자가 비밀번호를 분실한 경우 **`비밀번호 재설정`** 을 누릅니다.
새 임시 비밀번호가 발급되고 **기존 비밀번호는 즉시 사용할 수 없게 됩니다.**
대장 기록과 변경 이력은 그대로 유지됩니다.

### 계정 회수

인사 이동·퇴사 시 **`비활성화`** 를 누릅니다. 즉시 로그인이 차단됩니다.
그 사실을 월간 점검 기록에 남기십시오.

> **계정은 삭제할 수 없습니다. 비활성화만 됩니다.**
> 그 계정이 남긴 변경 이력의 수행자 정보를 보존해야 하기 때문입니다.
> 삭제하면 과거 기록의 「누가」가 사라집니다.

필요하면 같은 버튼으로 다시 활성화할 수 있습니다.

### 자신에 대한 제한

자기 계정에는 **`본인`** 표시가 붙고 두 가지가 막혀 있습니다.

- 자신의 권한 변경 (드롭다운이 잠김)
- 자신의 계정 비활성화 (버튼이 표시되지 않음)

마지막 관리자가 스스로 권한을 내리거나 계정을 잠그면 아무도 계정을 관리할 수 없게 되기 때문입니다.
서버에서도 함께 차단합니다.

> **관리자 계정을 두 개 이상 두십시오.** 관리자가 한 명뿐이면 그 계정의 비밀번호를
> 분실했을 때 화면으로 복구할 수 없고, DB 연결 문자열로 스크립트를 직접 실행해야 합니다.
> 감사 관점에서도 계정 관리 권한이 1인에게만 있는 구조는 지적될 수 있습니다.

## 7. 저장소

**모든 로그인 계정이 열람할 수 있습니다.**

대장은 Neon Postgres에 저장됩니다. 현재 Free 플랜은 용량 한도가 있고
시점 복구 기간이 짧으므로, **대장 화면만으로는 증적을 장기 보존할 수 없습니다.**

> **대장은 작성 도구이며 장기 보존 수단이 아닙니다.**
> 감사 증적으로 제출할 자료는 **월 1회 이상 CSV로 내보내 아카이빙 채널에 보관**하십시오.
> 반출 시점을 월간 점검과 맞추면 그 시점의 모집단과 판정이 함께 남습니다.

### 상단 통계

| 카드 | 의미 |
|---|---|
| 사용 용량 | 한도 대비 사용률(%)과 실제 용량 |
| 배포 건 | 대장에 기재된 건수 |
| 추가 여유 (추정) | 배포 건 평균 크기로 환산한, 더 담을 수 있는 건수 |
| 최근 증적 반출 | 마지막 반출 이후 경과일과 수행자 |

### 01 용량 사용률

게이지가 70%에서 노랑, 85%에서 빨강으로 바뀝니다.

> **화면의 용량은 참고치입니다.** Neon이 과금 기준으로 집계하는 용량은
> 변경 이력(WAL)을 포함하므로 이 값보다 큽니다. 한도가 임박하면
> Neon 콘솔에서 실제 값을 확인하십시오.

### 02 테이블별 사용량

시간이 지나면 **변경 이력이 가장 큰 비중을 차지합니다.** 기록이 쌓이기만 하기 때문입니다.

> **변경 이력을 용량 확보 목적으로 지우지 마십시오.** 통제 운영의 증거이므로,
> 지우면 그 기간의 변경 통제를 증명할 수 없게 됩니다.
> 한도에 근접하면 **반출 후 플랜 상향**이 올바른 순서입니다.

### 03 월별 등록 추이

배포일 기준 등록 건수입니다. 증가 속도로 반출 주기와 플랜 상향 시점을 판단합니다.

### 04 증적 반출 이력

언제 누가 어떤 범위로 증적을 내보내 보관했는지 기록합니다.
대장·점검 결과 CSV를 내보낼 때 자동으로 남습니다.

```
2026-07-02 10:00   김홍현   대장 · 214건 · 유형 정규 · 배포일 2026-07-01~2026-07-31
2026-07-02 10:02   김홍현   전체 백업 · 214건 · 전체
```

### 전체 대장 내보내기

우측 상단 **`전체 대장 내보내기`** 는 **필터와 무관하게 전체 배포 건**을 내보냅니다.
월 1회 보관용으로는 이쪽을 사용하십시오. 대장 화면의 `CSV 내보내기` 는
필터가 적용된 목록만 내보냅니다.

### 공지

아래 조건에서 **모든 화면 상단에 공지가 표시됩니다.** `저장소 보기` 를 누르면 이 화면으로 이동합니다.

| 조건 | 수준 | 조치 |
|---|---|---|
| 용량 85% 이상 | 조치 필요 | 증적 반출 후 플랜 상향 또는 이력 정리 검토 |
| 용량 70% 이상 | 확인 | 증적을 내보내 별도 보관 |
| 최근 반출 이후 35일 초과 | 확인 | 월 1회 이상 내보내 보관 |
| 반출 기록 없음 (배포 건이 있을 때) | 확인 | 대장을 내보내 아카이빙 채널에 보관 |

35일은 월간 점검이 월 1회이므로 한 달을 조금 넘긴 값으로 정한 것입니다.
